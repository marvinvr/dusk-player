# Development Workflow for Agents

This repo is active multi-agent territory. Work narrowly, verify against the current tree, and do not touch files outside the requested scope.

## First-Read Order

1. `AGENTS.md` for local agent rules, build expectations, and references.
2. `AGENTS.local.md` when present for checkout-specific constraints.
3. `docs/codebase-map.md` for code boundaries and the current mental model.
4. `docs/product-and-scope.md` for product intent and long-lived constraints.
5. `STYLE.md` before any UI change.
6. `project.yml` before source-file, target, resource, or framework changes.
7. `README.md` for public setup and feature status.
8. Source layout with `find Dusk/Sources -maxdepth 3 -type f | sort`.

Docs can lag source. Confirm current behavior in code before making specific claims.

## Source-of-Truth Files

- `project.yml`: Xcode targets, schemes, sources, resources, deployment targets, framework embedding, Swift settings.
- `Dusk.xcodeproj`: generated by XcodeGen; keep it synced, do not hand-edit it.
- `STYLE.md`: visual tokens, materials, spacing, typography, and UI guardrails.
- `docs/codebase-map.md`: intended code boundaries and extension patterns.
- `docs/product-and-scope.md`: product requirements and non-goals; check
  `project.yml` for current platform details.
- `Frameworks/`: vendored VLCKit binaries and the locally built
  `DuskDovi.xcframework` (all git-ignored). Refresh VLCKit only when explicitly asked.
- `Native/DuskDovi/`: the Rust crate behind `DuskDovi.xcframework` (Dolby Vision 7 → 8.1
  sample conversion over quietvoid's `dolby_vision`); its C header is the frozen ABI.

## Where New Files Go

- App entry, theme, and navigation shell code: `Dusk/Sources/App/`.
- New Plex endpoints: the matching `PlexService+*.swift` concern file.
- Plex response and app-facing media types: `Dusk/Sources/Models/`.
- Playback engine details: `Dusk/Sources/Playback/`.
- Player UI, overlays, sheets, and coordinator behavior: `Features/Player/`.
- Detail screens and detail-only shared pieces: `Features/Detail/`.
- Broad reusable UI, formatting, and presentation helpers: `Shared/`.
- Offline download implementation: `Dusk/Sources/Downloads/`.
- Download-facing screens: `Dusk/Sources/Features/Downloads/`.
- Resources: `Dusk/Resources/`; iOS support plist files: `Dusk/Support/`.

Prefer existing files and same-type extension patterns for small additions. Add a file when the code is a distinct concept or an existing type is already split by concern.

## Architectural Guardrails

- Plex is the only backend. Do not add provider abstractions without a real second backend.
- Views do not call the network directly. SwiftUI views talk to `@Observable` view models; view models call `PlexService`.
- Use async/await. Avoid Combine except when wrapping callback APIs.
- Keep AVPlayer/VLCKit specifics in `Playback/` behind `PlaybackEngine`.
- Keep engine-agnostic player UI in `Features/Player/`.
- Use platform-specific shells for meaningful iOS/tvOS layout differences.
- Use `#if os(tvOS)` close to platform-specific behavior.
- Direct play is the startup baseline. Manual quality changes may request Plex
  transcoding, but stored preferences must not start video transcoding
  automatically.

## Style Guardrails

- Native vibes, not orange: system controls and Liquid Glass first, no colour tint on them.
- Use `Color.duskBackground`, `Color.duskSurface`, `Color.duskTextPrimary`, and `Color.duskTextSecondary`. `Color.duskAccent` (Sunset Coral) is brand only: Supporter page and App Icon picker.
- Do not introduce ad-hoc UI colors such as `.orange`, `.blue`, `.green`, or `.purple`.
- Use system materials where `STYLE.md` calls for glass overlays/navigation.
- Follow `STYLE.md` for radii, borders, typography, and tvOS focus treatment.

## XcodeGen and Project Maintenance

- Edit `project.yml` for project settings, targets, resources, frameworks, or deployment target changes.
- Run `xcodegen generate` after changing `project.yml`.
- Run `xcodegen generate` after adding, removing, or renaming files under `Dusk/Sources`.
- Commit regenerated `Dusk.xcodeproj` only when it changed because of your intentional project/source-file change.
- If `xcodegen` is unavailable, report the verification gap instead of hand-editing generated project files.

## VLCKit Bootstrap

- Xcode Cloud (no longer used for releases) ran `ci_scripts/ci_post_clone.sh`, and `scripts/testflight.sh`
  runs the same installer. `ci_post_clone.sh` calls
  `ci_scripts/install_vlckit.sh` to fetch both pinned framework archives before
  any target builds.
- The archives are checksum-verified. Network, TLS, and CDN transfer failures
  are retried, with partial downloads resumed; do not weaken the checksum or
  replace this with an unverified framework fallback.
- The archives are Dusk's own build (TrueHD), assets of the release
  `vlckit-<version>` (currently `vlckit-3.7.3-dusk2`) in the PRIVATE repo
  `marvinvr/dusk-vlckit` — private on purpose: a public binary with the
  Dolby TrueHD decoder is a distribution Marvin decided against. The
  installer downloads them with `gh release download`, so it needs `gh` with a
  login (or `GH_TOKEN`) that can read that repo; `gh auth status` checks it.
- Without that access the installer falls back to VideoLAN's stock 3.7.3
  (public CocoaPods archives, thinned to arm64, also checksum-pinned). The app
  builds and runs with it; Playback Info's "VLCKit Build" row says "Stock
  VLCKit 3.x" and TrueHD goes through Plex. Once access exists, the next run
  replaces the stock install. `DUSK_VLCKIT_REQUIRE_DUSK=1` makes the fallback
  an error; `scripts/testflight.sh` sets it, so a release can never ship the
  stock build by accident.
- "Already installed" is decided from each slice's `DuskVLCKitBuild` stamp
  (Dusk) or the `vlckit-installed.txt` marker the installer writes into each
  xcframework (stock), never from the tracked `Frameworks/VLCKit-VERSION.txt`:
  that file names the new version as soon as you pull, while the git-ignored
  frameworks (and the copies `scripts/testflight.sh` takes from the checkout)
  are still old. A stock fallback leaves `VLCKit-VERSION.txt` untouched.
- `scripts/verify_embedded_vlckit.sh` (a post-build phase) also fails the
  build when the embedded VLCKit weak-links libSystem functions older OS
  versions lack, and `build_vlckit.sh` refuses to package such a build.
  3.7.3-dusk1 was built with the Xcode 27 SDK, whose `pipe2` exists only on
  iOS/tvOS/macOS 27. libvlc weak-linked it and jumped to NULL on its first
  socket/pipe, i.e. every VLC network open, on tvOS 26 and on Macs running
  macOS 26 (#27). Simulators cannot show this: they resolve libSystem
  against the host macOS. dusk2 adds `vlc-patches/0102`, which makes
  `vlc_pipe` use `pipe()` on Apple platforms.

## VLCKit Build

- `ci_scripts/build_vlckit.sh [ios|tvos|all]` builds MobileVLCKit/TVVLCKit
  from source: VLCKit tag 3.7.3 (pinned commit, libvlc 3.0.x at VLCKit's
  tested hash), arm64 device + arm64 simulator slices. Manual only; nothing
  in CI runs it. iOS and tvOS use separate trees under `.build/vlckit/`, so
  `build_vlckit.sh ios & build_vlckit.sh tvos` runs both in parallel. A cold
  build compiles VLC's own toolchain and every contrib; trees are reused, and
  `DUSK_VLCKIT_CLEAN=1` starts over. Logs: `.build/vlckit/<platform>.log`.
- Patches: `ci_scripts/vlckit-patches/` apply to the VLCKit checkout (build
  script: arm64-only packaging, iOS/tvOS 15 minimum, current Xcode);
  `ci_scripts/vlc-patches/` (0100+) are appended to VLCKit's own libvlc
  series, which `buildMobileVLCKit.sh` git-am's onto vlc. 0100 re-enables
  TrueHD/MLP (read "Dolby TrueHD decoding" in `playback.md` for the licensing
  decision), 0101 fixes tvOS multichannel output, 0102 keeps libvlc off
  `pipe2` (OS 27+ only, see VLCKit Bootstrap).
- The script fails unless `libavcodec.a` defines `ff_truehd_decoder` and
  `ff_mlp_decoder`, stamps each framework's Info.plist (`DuskVLCKitBuild`,
  `DuskVLCKitTrueHD`, read by `VLCKitBuildInfo`), and writes
  `<Name>-<version>.tar.xz` + `.sha256` to `.build/vlckit/out/`.
- Releasing a new build: bump `DUSK_VLCKIT_BUILD` in `build_vlckit.sh`, build
  both platforms, then
  `gh release create vlckit-<version> --repo marvinvr/dusk-vlckit
  .build/vlckit/out/*.tar.xz .build/vlckit/out/*.sha256` (upload the archives
  unchanged; repacking changes the checksums), and pin
  `VLCKIT_VERSION` plus both SHA-256 values in `install_vlckit.sh` in the same
  commit. Test locally before publishing with
  `DUSK_VLCKIT_CACHE_DIR=.build/vlckit/out ci_scripts/install_vlckit.sh`.
- The libvlc version string stays `3.0.x`; the stamp is what distinguishes
  Dusk's build from VideoLAN's.

## DuskDovi Bootstrap

- `Frameworks/DuskDovi.xcframework` is a static library (iOS + tvOS, device + simulator,
  arm64 only) built from `Native/DuskDovi` and linked into both apps, never embedded.
  It is git-ignored; after cloning run `./ci_scripts/install_dusk_dovi.sh` once (needs
  [rustup](https://rustup.rs)). `ci_post_clone.sh` runs it too, installing rustup on CI.
- The installer stamps a hash of the crate, `Cargo.lock`, the toolchain pin, the build
  script and the `project.yml` deployment targets into the xcframework, and is a no-op
  until one of them changes. `scripts/build_dusk_dovi_xcframework.sh` forces a rebuild.
- Toolchain: pinned in `Native/DuskDovi/rust-toolchain.toml`, installed with the four
  Apple targets on demand. Deployment targets are read from `project.yml`.
- Homebrew trap: `/opt/homebrew/bin/cargo` and `rustc` usually come first on PATH and
  have no iOS/tvOS standard library (`can't find crate for core`). Recent rustup no
  longer puts the toolchain first on PATH for `rustup run`, so even
  `rustup run 1.96.0 cargo build` reaches Homebrew's `rustc`. The build script pins
  `RUSTC` and cargo via `rustup which`; do the same for manual builds:
  `RUSTC="$(rustup which rustc --toolchain 1.96.0)" "$(rustup which cargo --toolchain 1.96.0)" test --manifest-path Native/DuskDovi/Cargo.toml`.
- Changing `dusk_dovi.h` means bumping `DUSK_DOVI_ABI_VERSION` (and the check in
  `DoviBridgeTests`). New crates in `Cargo.lock` need an entry in
  `Dusk/Resources/ThirdPartyNotices.txt` and `Native/DuskDovi/THIRD_PARTY_LICENSES.md`.

## Metal Toolchain

- Xcode 26 and later ship the Metal compiler as a separate component that is not
  installed out of the box, so `ci_post_clone.sh` installs it before the build.
  Run `xcodebuild -downloadComponent MetalToolchain` once locally too, after
  installing a new Xcode, or `VideoEnhancementShaders.metal` fails to compile.
- The failure reads `cannot execute tool 'metal' due to missing Metal Toolchain`.
  It is preceded by a red herring — a warning that the shader's `.dia`
  diagnostics file does not exist, because `metal` never ran to write one.
- The Xcode Cloud trap: the images stage the component as an *exported bundle*
  under `~/Library/Developer/DVTDownloads` without ever importing it. A plain
  `-downloadComponent` then fails with "Metal Toolchain is already imported" and
  installs nothing, so the bundle has to be imported with
  `xcodebuild -importComponent MetalToolchain -importPath <bundle>`. Verify with
  `xcrun --sdk iphoneos metal --version`, not with the exit code of either
  command — that is what the script checks, and it fails the post-clone step
  loudly rather than letting the build die in `CompileMetalFile`.

## TestFlight (`scripts/testflight.sh`)

Builds a commit, signs it for the App Store and uploads it to TestFlight, then waits until
App Store Connect has processed it. Replaces Xcode Cloud. Also the mmux process **TestFlight** (`mmux start TestFlight`).

```bash
scripts/testflight.sh [ref] [--platform ios|tvos|all] [--dry-run] [--no-wait]
```

- `ref`: commit or ref, default `origin/main` (fetched first). The build comes from `git archive`
  of that commit, so local changes never end up in it.
- `--platform`: `ios` (scheme `Dusk`), `tvos` (scheme `Dusk-tvOS`) or `all` (default). With `all` both
  platforms run in parallel, each with its own DerivedData, so their uploads and App Store Connect
  processing waits overlap (~10 min → ~5 min; the archives themselves don't compete for the CPU).
  Progress lines are prefixed `[testflight ios]` / `[testflight tvos]`, details in each platform's
  `archive.log` / `export.log` in the work dir. One failing platform doesn't stop the other.
- `--dry-run`: archive, sign and export the `.ipa` locally, no upload. `--no-wait`: upload only.
- Before building it copies the checkout's `Frameworks/*.xcframework` into the build copy and runs
  `ci_scripts/ci_post_clone.sh` (verifies VLCKit or downloads the pinned version, rebuilds
  DuskDovi only if its sources changed, installs the Metal toolchain).
- Apple assigns the build number (`manageAppVersionAndBuildNumber`); versions in the repo are
  never changed. A VALID build lands in the internal TestFlight group automatically.

One result line per platform at the end, OKs first; the last line (and so the exit code) is always `TESTFLIGHT OK platform=<p> build=<n> state=VALID id=<build id> commit=<sha>` or
`TESTFLIGHT FAIL platform=<p> code=<n> reason=<text> log=<work dir>`.

| Exit | Meaning |
| --- | --- |
| 0 | OK (VALID, or EXPORTED with `--dry-run`) |
| 2 | Usage |
| 3 | Signing: no valid App Store profile for a bundle id (e.g. a new extension), profile expired or INVALID in App Store Connect (capabilities changed), entitlement or app group missing from the profile |
| 4 | Archive (compile) failed, see `archive.log` |
| 5 | Export / upload failed, see `export.log` |
| 6 | Processing ended INVALID (App Store Connect mails the details) |
| 7 | Processing not finished after 45 min (the build may still turn VALID) |
| 8 | Source: unknown ref, `xcodegen`, build settings |
| 9 | Another build of this repo is running |
| 10 | Credentials missing |
| 1 | Unexpected error |

Setup (once per machine, nothing of it in the repo): an env file at `ASC_ENV_FILE` (default
`~/.config/testflight/env`, mode 600) or the same variables in the environment:

```bash
ASC_KEY_ID=<App Store Connect API key id>
ASC_ISSUER_ID=<issuer id>
ASC_KEY_PATH=<path to the .p8>
SIGNING_KEYCHAIN=<optional: keychain with the "Apple Distribution" identity>
SIGNING_KEYCHAIN_PASSWORD_FILE=<optional: file with its password>
```

plus an installed App Store provisioning profile per bundle id and platform (iOS and tvOS are separate profiles) (app and every extension: tvOS also needs one for `com.dusk-player.app.topshelf`), made
with that distribution certificate. Both tvOS profiles must include the App Group
`group.com.dusk-player.app`. The script picks the newest matching one, checks it is
ACTIVE in App Store Connect and covers the target's entitlements, and signs manually with it
(the project itself keeps automatic signing).

## Verification Commands

After code changes, run compile-only verification. Do not run tests or launch the app/simulator unless asked.

```bash
xcodebuild -project Dusk.xcodeproj -scheme Dusk -configuration Debug -destination 'generic/platform=iOS Simulator' ARCHS=arm64 ONLY_ACTIVE_ARCH=YES build
```

The arm64 override is required because the vendored iOS `MobileVLCKit.xcframework` is thinned to arm64 only (device and simulator).

When tvOS is relevant:

```bash
xcodebuild -project Dusk.xcodeproj -scheme Dusk-tvOS -configuration Debug -destination 'generic/platform=tvOS Simulator' ARCHS=arm64 ONLY_ACTIVE_ARCH=YES build
```

The arm64 override is also required for the vendored tvOS
`TVVLCKit.xcframework`; its slices are likewise thinned to arm64 only.

For docs-only changes, a build is normally unnecessary. Verify the file and `git status --short`.

### Large-library reproduction

`scripts/mock_large_plex.py` is a stdlib-only mock of plex.tv plus one PMS with a
synthesized library (60k movies, 12k shows by default). Section queries pay a
per-row scan cost (`--scan-us`, serialized through `--db-workers`), the way a big
PMS on a NAS behaves; every request is logged with its arrival time and duration,
which is the measurement. Point a Debug build at it with the screenshot-mode launch
arguments (`-DuskScreenshotMode YES -DuskScreenshotPlexTV http://127.0.0.1:47600
-DuskScreenshotScreen movies|shows|library`, see `docs/screenshots.md`) and take
`simctl io screenshot`s at fixed offsets. Use it before and after touching library,
hub or recommendation loading. `--photos 5000` adds a photo library (section 3:
year/month and trip albums, loose root photos, ~5% clips) that answers the
`type=` / `parent=` / `clusterZoomLevel=1` queries and serves generated plasma JPEGs
from `/photo/:/transcode` (ImageMagick, cached in `build/mock-photo-images`); open it
with `-DuskScreenshotScreen photos`. Movies and TV Shows carry eight Plex collections
(manual ones tag their titles, smart ones do not; "Everything Electric" is big enough
to page); `--collection-mode 0|1|2` sets the sections' Collections pref, and
`-DuskScreenshotScreen collections` (plus `-DuskScreenshotItemType show`) opens a
library's Collections grid, `detail` with `-DuskScreenshotItemType collection
-DuskScreenshotItem 800000` a collection. Movies whose rating key is divisible by 4
have 2-5 local extras (`/library/metadata/{rk}/extras`, extra keys from 700000), and
the first show (rk 1001 + `--movies`, 61001 by default) is the only one with seasons: 2 x 4
episodes from rk 750001, with extras on the show, Season 1 (750001) and S1E1 (750002).
The other shows have no seasons. Clip playback cannot be exercised there (no media
files). Its costs are a model, not a real server: compare
builds against each other, not against absolute numbers.

## Git and Push Expectations

- Check `git status --short` before editing and before finishing.
- Assume unrelated changes belong to other agents. Do not revert, stage, commit, or overwrite them.
- If asked to commit/push without branch instructions, use the current branch.
- If asked to commit with unrelated changes present, commit only your changes.
- Avoid destructive commands unless the user explicitly requested them.
- Before publishing, inspect the diff and confirm it matches the requested scope.

## Common Traps

- Forgetting `xcodegen generate` after Swift file adds/removes/renames.
- An app extension's hand-written `Info.plist` must list `arm64` under
  `UIRequiredDeviceCapabilities`, or the TestFlight upload is rejected as an invalid bundle
  (`DuskTopShelf/Info.plist`).
- Building iOS simulator without `ARCHS=arm64 ONLY_ACTIVE_ARCH=YES`.
- Treating `Dusk.xcodeproj` as hand-authored.
- Adding view-level networking instead of using view models and `PlexService`.
- Reintroducing broad backend abstractions while Plex is the only backend.
- Duplicating formatting, state views, posters, or grids instead of checking `Shared/`.
- Putting AVPlayer/VLCKit-specific behavior into generic player UI.
- Assuming docs platform versions are newer than `project.yml`.
- Editing vendored VLCKit binaries or unrelated worktree changes.
- Building `Native/DuskDovi` with Homebrew's `cargo` (see DuskDovi Bootstrap).
